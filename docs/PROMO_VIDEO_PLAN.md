# Making a promo video for HomeDesigner

Draft **2026-08-26**. Assesses
[OpenMontage](https://github.com/calesthio/OpenMontage) — the agentic video
system from the linked post — as the way to produce marketing video for the app,
and sets out what actually has to happen first.

---

## Verdict

**Use it, but not for the reason the post gives.**

The post sells it as "throw in one sentence of plain language and it runs script,
footage, voiceover, subtitles and the finished cut". That is true, and for
HomeDesigner it is the wrong half of the tool. The sentence-to-video mode
assembles **stock footage**, and a stock-footage video for a floor-plan app sells
nothing — the product *is* the picture. Google agrees, as a matter of policy:
a Play preview video should be **at least 80% actual app experience**, and "fake
UI, misleading visuals, or showing features that don't exist" are grounds for
rejection.

What makes it worth using is the **Screen Demo pipeline** — "polished software
walkthroughs" — which explicitly supports real capture via a
`playwright-recording` tool "only when the demo is a real app UI". That is the
mode we want: **our footage, its script/voiceover/subtitles/edit.**

**The tool is not the bottleneck. Footage is.** And the good news is that this
repo is already three quarters of the way to a capture rig.

---

## 1. Licence — clear, unlike last time

OpenMontage is **AGPL-3.0**. Worth stating plainly, because
`docs/HOME_SCAN_VIABILITY.md` just rejected a dependency on licence grounds and
the two cases are opposite:

| | Inria 3DGS | OpenMontage |
| --- | --- | --- |
| Licence | Non-commercial research | AGPL-3.0 (OSI open source) |
| Commercial use | **Prohibited** | **Permitted** |
| What it would be used for | Code shipped in the product | A tool run locally to make a file |

AGPL obligations trigger on **distributing the software** or **offering it to
users over a network**. Running it on your own machine to render an MP4 is
neither. The video it produces is your output, not a derivative of the software.

The one rule to keep: **do not vendor OpenMontage into this repo, the Worker, or
the app bundle.** Keep it as a separate checkout beside the project, the same way
`node_modules` is not committed. Under AGPL, folding it into a shipped product
would put obligations on HomeDesigner itself.

## 3. Getting the footage: `tools/capture-clips.mjs`

Added in this change. It is a sibling to `tools/screenshots.mjs` and reuses its
entire setup — same `vite preview` spawn, same `?pro=1` (show the full product,
no locks), same `hd-intro-enabled=0` / tour-dismissed init script, same
selectors — but records **video** instead of stills:

```bash
npm run build && node tools/capture-clips.mjs      # 2D clips, phone-portrait
CAPTURE_GPU=1 node tools/capture-clips.mjs         # + the 3D clips, on a GPU box
LANDSCAPE=1 CAPTURE_GPU=1 node tools/capture-clips.mjs   # landscape, for Play
ONLY=02-draw-walls node tools/capture-clips.mjs    # re-shoot one clip
```

Five clips into `store/clips/`: the project gallery, **walls being drawn live**
corner by corner, furnishing from the catalog, the 2D→3D reveal, and an orbit of
the finished home. One `.webm` each, so the edit can pick and trim.

It differs from the screenshot harness in one deliberate way: it does **not**
force `reducedMotion: 'reduce'`. The app's transitions are part of what a promo
is selling.

### Verified in this session

Run end to end on this container, and fixed twice off the results.

- **It works** — but only after two real bugs, both worth knowing about before
  anyone extends it.
- **The 2D clips are good footage.** The walls clip draws a closed rectangle
  corner by corner with the live `3.20 m · 270°` readout on screen, in 11s.
- **The 3D scene renders correctly under software GL** — walls, furniture, the
  deck, the tree, the parasol, real shadows. Content is not the problem; speed
  is.

**Bug 1 — the tool dock is not on screen at phone width.** The first run's
walls clip failed with a 30s click timeout and recorded 40 seconds of an empty
grid. On a 390px viewport the tools live behind the **Build** tab, so the dock
has to be opened before a tool can be picked. Positional selectors are also a
trap here: `.tool-dock` interleaves `.dock-sep` separators between buttons, so
`.dock-btn:nth-child(2)` is not the second tool. Select by `aria-label`, and
`dispatchEvent('click')` rather than `click()` — the drawer backdrop swallows
real pointer events, which is why `screenshots.mjs` already does the same.

**Bug 2 — Playwright never scales a page up.** `recordVideo.size` only ever
scales a page *down* to fit; asking for a larger size parks the page 1:1 in the
corner of a mostly-empty frame, which is what the first run produced. Record at
true phone CSS pixels and upscale in post:

```bash
ffmpeg -i store/clips/04-to-3d.webm -vf scale=1080:-2:flags=lanczos \
       -c:v libx264 -crf 18 -pix_fmt yuv420p 04-to-3d.mp4
```

(Playwright ships its own ffmpeg if the system has none — look under the
browsers path for `ffmpeg-*/ffmpeg-linux`.)

**And the finding that decides where capture happens: 3D motion is not viable
headless.** Measured, same run, same machine:

| Clip | Record time |
| --- | --- |
| `01-home` | 4.9s |
| `02-draw-walls` | 11.4s |
| `03-furnish` | 11.0s |
| `04-to-3d` | 28.7s |
| **`05-orbit-3d`** | **656.5s** |

Eleven minutes to record a four-second drag, because every frame is a full
software re-render of a shadowed, post-processed scene — and the result still
judders. So the two 3D clips are now **opt-in**: `CAPTURE_GPU=1` on a machine
with a GPU (which also drops the software-GL flags), or `CAPTURE_3D=1` to record
them in software anyway and wait. The 2D clips stay the fast default, and
`ONLY=<clip>` re-shoots a single one.

**The best footage is not headless at all — it is a screen recording of the real
Android build on a real phone.** It is a phone app; that footage is truest,
already the right aspect ratio, and has no GPU caveat. Use `capture-clips.mjs`
for repeatable, scriptable, locale-able coverage — it can re-shoot every clip in
all five listing locales the way `screenshots.mjs` already does for stills — and
the phone for the hero shots.

## 4. Requirements check

| OpenMontage needs | Here | Workstation |
| --- | --- | --- |
| Python 3.10+ | ✅ 3.11 | check |
| Node 18+ (22+ for HyperFrames) | ✅ 22 | check |
| FFmpeg | ❌ not installed (apt-installable; Playwright also ships one under `ffmpeg-*/ffmpeg-linux`) | check |
| GPU | ❌ (only needed for *local AI video generation*, which we do not want) | — |
| API keys | none required | — |

It is driven by an AI coding assistant — Claude Code is explicitly supported, so
this is drivable from a session like this one. Setup is `make setup`; the free
path is Piper TTS for narration, Remotion or HyperFrames for composition, FFmpeg
for post. Budget cap defaults to $10 with a $0.50 per-action approval threshold;
zero-key operation is a first-class mode, so the first cut can cost nothing.

**We would use almost none of its generative surface.** No Kling, no Runway, no
Veo, no FLUX — every one of those makes footage we specifically must not use.
What earns its keep is the unglamorous half: script structure, narration,
subtitles, pacing, music bed, and rendering consistent cuts at several aspect
ratios.

## 5. Recommended plan

1. **Capture on the workstation, not headless.** `npm run build && CAPTURE_GPU=1
   node tools/capture-clips.mjs`, plus a landscape pass. Screen-record the
   Android build for the hero 3D walkthrough.
2. **Write the script first, in three beats** — the same three the landing page
   already uses and that the store listing is built around: *Sketch → Furnish →
   Experience*. It is proven copy; do not let a generator invent new positioning.
3. **Cut three deliverables from one capture set:**
   - **Play listing:** landscape, ~30s, front-load the 2D→3D reveal because only
     the first 30s autoplays. Upload to YouTube, embedding on, monetisation off,
     paste the clean full URL.
   - **Landing page:** a real-app cut to sit alongside (or replace) the current
     8s render in the scroll-scrubbed section. Keep it short — it is scrubbed by
     scroll position, not played.
   - **Social:** 9:16, 15–20s, no voiceover needed, subtitles burned in.
4. **Keep OpenMontage outside the repo.** Separate checkout; commit only the
   rendered outputs and the capture script.
5. **Honesty check before publishing:** everything on screen must be a real
   feature at the shipped version. `?pro=1` shows the full product, so say Pro
   where a Pro feature is on screen.

## 6. Open questions

1. Does the workstation have FFmpeg and a GPU good enough for smooth capture, or
   is phone screen-recording the primary source?
2. Voiceover or captions only? Piper TTS is free and offline; a paid voice
   (ElevenLabs) is the one place spending a little may be worth it, and it is
   also the one that dates fastest.
3. Do we re-shoot per locale? `screenshots.mjs` already does five for stills;
   video multiplies the edit cost, and subtitles may be enough.
4. Does the landing page's scroll-scrubbed film get replaced by real-app footage,
   or keep the render as the "dream" and add real footage below it?
